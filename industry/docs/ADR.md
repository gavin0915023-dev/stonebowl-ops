# 架构决策记录（ADR）

记录"为什么这么做"，供答辩、评审与后续维护追溯。状态：Proposed（提出）/ Accepted（已采纳）/ Deprecated（已废弃）。

## ADR-001 · 后端采用四语言拆分

**状态**：Deprecated（演示阶段已采纳；行业化阶段建议收敛）

**背景**：原项目把订单核心（Java 17 / Spring Boot）、余票查询（Go）、电子票验签（Rust）、前端（React/TS）拆成四个服务，用 Compose 编排。

**决策**：当时采纳，因为它清晰展示了多语言集成、服务边界与跨语言验签链路，作为教学/演示原型有展示价值。

**后果**：
- 正面：职责边界清楚；Go 只读缓存与 Java 写入方的分工具说服力。
- 负面：三个额外进程、三次网络跳转、三套构建与依赖、三个健康检查点；Rust 验签超时会阻断核销；排障链路变长。
- 关键：**没有任何压测数据**证明余票查询或验签构成了独立瓶颈。

**行业化决策**：收敛为单应用服务 + 托管 PostgreSQL。除非压测证明某环节确需隔离，否则不保留独立服务。删除服务比增加监控更省成本。

## ADR-002 · 库存一致性由数据库事务独占，缓存不参与售卖

**状态**：Accepted

**背景**：余票展示有性能诉求，容易顺手用缓存值判断"能不能买"。

**决策**：
1. Java 在单个 `@Transactional` 内完成查重（幂等键唯一约束）、行锁、库存校验、预占、写单。
2. Go 的 2 秒有界缓存**只服务 `GET /availability` 的展示**，任何下单路径都重新查主库。
3. 定时释放每 60 秒扫描 15 分钟未支付订单，加锁后释放，重复释放需幂等。

**理由**：缓存与数据库之间必然存在窗口，用它决定可售会超卖。宁可展示数字滞后，也不能让写入判断失真。

**后果**：余票展示可能短暂不准（可接受）；库存正确性由唯一约束 + 行锁 + 事务保证。需要并发压测持续验证（见 `loadtest/order-race.mjs`）。

## ADR-003 · 数据库变更必须版本化且可拒绝启动

**状态**：Accepted

**背景**：订票使用 `spring.jpa.hibernate.ddl-auto: update`，运行时自动改表；生产环境这会导致结构漂移、无法审计、无法回滚。

**决策**：
1. 订票改用 Flyway，`ddl-auto: validate`，所有结构变更走 `V{n}__*.sql`。
2. 采纳订餐项目已有的更严格做法：把**迁移文件 SQL 内容的 SHA256 写进文件名**，启动时比对已应用历史，出现编辑/删除/重排一律拒绝启动，并在事务表内记录执行。
3. 迁移只追加，不修改已应用版本；升级前先备份。

**后果**：多一点流程成本，换来可审计、可回滚、多副本安全。代价是首次切换需要基于现有库做一次基线迁移并核对。

## ADR-004 · 演示模式与生产模式物理隔离，默认拒绝启动

**状态**：Accepted

**背景**：原 `application.yml` 中 `demo-payments` 默认 `true`，`ticket-secret` 与 `staff-key` 带可用的弱默认值，`ALLOWED_ORIGIN` 写死 `localhost:5173`。运维若漏配环境变量，服务会带着模拟支付和弱密钥"正常"启动，属于高危静默失败。

**决策**：
1. 生产配置所有必需项**不设默认值**，缺失即启动失败（fail-fast）。
2. 新增 `StartupGuard`：校验密钥长度 ≥32、非示例值、`demo-payments` 在生产 profile 必须为 `false`、来源不得为 localhost。
3. 演示配置仅用于本地，且显式标注；两份配置不共用同一套默认口令。

**后果**：部署前必须显式配置 secrets，杜绝"忘设变量也能跑"。这也是 CI 与发布清单的强制检查项。

## 附：被明确拒绝的方案

| 方案 | 拒绝理由 |
|---|---|
| 用缓存判断库存以提升下单性能 | 一致性窗口导致超卖，违反 ADR-002 |
| 验签服务超时时放行核销 | fail-open 会造成重复核销与资损，必须 fail-closed |
| 用"模拟支付接口"占位真实支付 | 会让人误以为具备收款能力，属误导；真实支付需要商户资质，不是接口形状问题 |
| 运行时自动同步表结构 | 无法审计与回滚，违反 ADR-003 |
